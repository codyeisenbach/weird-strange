# Weird Strange

## Archive (`/archive`) and admin editing (`/admin`)

README.md ("Features implemented in this repo") already covers the surface facts — schema, routes, cache tags, the two-layer auth gate. This section only adds what isn't obvious from reading that once: the gotchas, the *why*, and things a future change is likely to get wrong.

**Four archive tables today, not five — `artworks` is the primary content unit, not artists/publications.** The archive was originally artist- and publication-centric with flat product-link join tables (`artist_products`, `publication_products`) and a manually-curated `artist_publications` join table. All three were **dropped** (pre-launch, no migration cost) in favor of `artworks` (`supabase/migrations/20260817151312_artworks.sql`) — a real content row per piece of (public-domain, AI-restored) cover art, with `artist_id` (required FK), `publication_id` (nullable FK), `placement` (free text — `front_cover`/`back_cover`/`interior`/etc., unvalidated), `description`, `image_path`/`image_alt`, and its own `artwork_products` join table to Shopify handles. The artist↔publication relationship is now **derived** from shared artworks (`dedupeByEarliestArtwork()` in `lib/archive/index.ts`) rather than separately maintained — an artist's publications list is `distinct publication_id from artworks where artist_id = X`, ordered by each publication's earliest linked artwork. Don't reintroduce a manual artist↔publication join table; two sources of truth for the same relationship is exactly what this replaced. Route: `/archive/artworks[/slug]`.

**Column name still lies about its own content.** `artwork_products.shopify_product_id` stores a Shopify product **handle** (string slug, e.g. `"bizarre-vintage-tiger-tee"`), not a numeric id or GID, despite the name — same convention the old `artist_products`/`publication_products` used before they were dropped. `resolveProducts()` in `lib/archive/index.ts` queries the Storefront API with `handle:x OR handle:y OR ...`. One artwork can link multiple products (e.g. a shirt and a print made from the same piece) via `artwork_products`, and the reverse lookup (`getArtworksForProductHandle`) is what powers the product page's structured data — see below.

**Stale Shopify products vanish silently, not with an error.** `resolveProducts()` drops any handle that doesn't resolve to a live product (deleted/unpublished in Shopify) with no error surfaced anywhere — the archive page just shows one fewer product tile. If someone reports "a product disappeared from an artist's page," check whether the product still exists/is published in Shopify before assuming a bug in this code.

**Publications have an `issue_date` free-text column** (e.g. `"Nov 1942"`, `"Fall 42"`, `"1942"` — deliberately unstructured, no parsing/normalization, same convention as `artworks.placement`) — it lives on `publications`, not `artworks`, because one issue can have multiple artworks (front cover, back cover) that should share one date rather than risk drifting apart if set per-artwork. It's editable on the publication's own edit page and shown read-only (linking back to the publication) on any artwork linked to it — don't add a duplicate editable date field to the artwork editor, since that row doesn't own this data. Editable via `WikiEditable`'s (`components/archive/wiki-editable.tsx`, shared by the artist and publication edit pages) optional `extraFields` prop — a list of `{ name, label, initialValue, placeholder? }` rendered as plain text inputs above the body textarea, added specifically to support this field. Artists don't pass any and render identically to before this existed. Prefer extending this over forking a third near-duplicate of `WikiEditable`/`WikiEditableArtwork` for one more plain-text field; fork only when the new field genuinely isn't a plain text input (a relational `<select>`, a file upload) the way artwork's editor already had to.

**Artwork images are real now, and deliberately downscaled.** `uploadArtworkImage()` (`lib/archive/index.ts`) uploads to Cloudflare R2 via the S3-compatible API (`lib/r2/client.ts`, `@aws-sdk/client-s3`) and is wired into both the artwork create form (`NewArtworkForm`) and the artwork edit page (`ArtworkImageUpload`, uploads immediately on file selection via a Server Action). Every upload is resized server-side with `sharp` — capped at 1600px on the longest edge, re-encoded to WebP — **before** it ever reaches R2; the original full-resolution file is never stored anywhere, only ever held in memory for the request. This is deliberate, not a size-optimization afterthought: these are AI-restored/upscaled scans the user considers their own work product (the underlying public-domain art isn't protectable, but the restoration is), and serving only a capped web version is a soft deterrent against the images being lifted at full quality for someone else's merch — not a hard block, since a downscaled image can still be screenshotted, but it raises the bar. R2 env vars are **not** named `R2_*` — this repo uses `CLOUDFLARE_S3_API_DOMAIN` (bundles account id + bucket name into one URL, e.g. `https://<account-id>.r2.cloudflarestorage.com/weird-strange-media`, parsed apart in `lib/r2/client.ts`), `CLOUDFLARE_S3_ACCESS_KEY`, `CLOUDFLARE_S3_SECRET_ACCESS_KEY`. Public reads go through `NEXT_PUBLIC_ARCHIVE_IMAGE_BASE_URL` (currently `media.weirdstrange.com`, a Cloudflare custom domain bound to the R2 bucket) — **any new image hostname must also be added to `next.config.ts`'s `images.remotePatterns`**, or `next/image` throws a 500 (`Invalid src prop ... hostname is not configured`); this bit a real domain migration once (see git history) and isn't automatically discovered from `NEXT_PUBLIC_ARCHIVE_IMAGE_BASE_URL` alone.

**Products can be linked to an artwork from the admin UI now — `ProductPicker`/`LinkedProductsEditor`.** `components/archive/product-picker.tsx` is a Headless UI `Combobox` (not a plain `<select>` — the dropdown needs to show a thumbnail + title + the Shopify Storefront GID per row, which `<option>` can't render) searching the full product catalog (`getProducts({})`, capped at 100 by the existing Storefront query — not changed as part of this). "Product id" shown in the picker is the Storefront API's GID (`gid://shopify/Product/...`); this API has no separate numeric id, and the GID is display-only — the DB link still stores the handle. Wired into both artwork creation (`NewArtworkForm`, links submitted in the same `FormData` POST as everything else) and the artwork edit page (`LinkedProductsEditor`, immediate link/unlink via Server Actions, no form submit needed).

**Two Supabase server clients exist; archive writes deliberately use the one that bypasses RLS.** `getSupabaseServerClient()` (secret key, no session — used for *all* archive reads and writes) vs. `getSupabaseAuthServerClient()` (publishable key, cookie session, subject to RLS — used *only* for `auth.getUser()`/`signInWithOtp()`/`signInWithOAuth()`/`signOut()`, i.e. identity, never content). This is intentional: "admin" is an app-level email allowlist (`ADMIN_EMAILS`), not a Supabase Auth role, so there's no `authenticated`-role RLS policy that could enforce write access at the DB layer even if the auth-scoped client were used instead. All four archive tables have RLS enabled with exactly one policy each — public `select` for `anon`/`authenticated`, no `insert`/`update`/`delete` policy for anyone — so `requireAdmin()` is the *entire* write-authorization boundary, not RLS. Don't assume adding an RLS write policy would be redundant defense-in-depth; right now it would be the only DB-level check that exists at all, since currently even a leaked publishable key + a real Supabase Auth session couldn't write (no policy permits it), only a leaked secret key could.

**`requireAdmin()` is checked in two layers, not one — both the Server Action wrapper *and* the data-layer write function itself.** Every write function in `lib/archive/index.ts` (`updateArtist`, `updatePublication`, `updateArtwork`, `createArtist`, `createPublication`, `createArtwork`, `uploadArtworkImage`, `linkArtworkProduct`, `unlinkArtworkProduct`) calls `requireAdmin()` as its own first statement, in addition to the `app/archive/actions.ts` Server Action that calls it before delegating. This was added deliberately after a security review found the data layer trusted every caller to have checked first — true for every *current* caller, but a landmine for any future one (a new action, a script, a route) that might forget. Don't remove either layer thinking it's redundant; the data-layer check is what makes a forgotten action-layer check fail closed instead of silently writing.

**Cache invalidation uses Next 15's newer API.** `updateTag(ARCHIVE_TAGS.artists | .publications | .artworks)` from `next/cache` — not `revalidateTag`/`unstable_cache`. `ARCHIVE_TAGS` (`lib/archive/index.ts`) is `{ artists: "archive-artists", publications: "archive-publications", artworks: "archive-artworks" }`; every detail-page read (`getArtist`, `getPublication`, `getArtwork`, and the product-page reverse lookup `getArtworksForProductHandle`) tags with **all three**, since any of the three content types can now embed data from any other (an artist page lists its artworks; an artwork page shows its publication's issue date; a product page shows its artwork's artist and publication) — an edit anywhere in the archive is treated as potentially visible everywhere else in it.

**Magic-link sign-in intentionally returns the same message whether or not the email is allowlisted or even has an account.** `sendMagicLink` (`app/admin/login/actions.ts`) does this on purpose, to prevent allowlist enumeration via the login form. Don't "improve" the error message to be more specific.

**The "Continue with Google" button has its own allowlist check now — don't remove it as "redundant."** `/admin/login` offers two sign-in paths: magic-link (only ever emailed to an already-allowlisted address, checked before Supabase is even called) and Google OAuth (`signInWithOAuth`, called directly from the browser with **no** pre-check — any Google account can *attempt* it). This was flagged in a security review: the OAuth path's safety depended entirely on Supabase's `enable_signup: false` (confirmed live on the production dashboard, not just in `supabase/config.toml`) refusing to auto-provision a session for an unrecognized account — a real but externally-controlled single point of failure this repo can't self-verify at build time. `app/admin/auth/callback/route.ts` now checks `isAdminEmail()` itself after *any* successful session exchange (OTP or OAuth) and calls `signOut()` immediately if it fails, before ever redirecting into `/admin` — so the allowlist is the enforced boundary on both paths, not just one, regardless of what the Supabase dashboard toggle is set to.

**`/admin/auth/callback` is deliberately exempt from the admin middleware gate** — not an oversight. Gating it would create a chicken-and-egg redirect loop, since it's what establishes the session the gate later checks. `middleware.ts`'s `ADMIN_GATE_EXEMPT` array is the enforcement point; only `/admin/login` and `/admin/auth/callback` are exempt, everything else under `/admin` is gated by prefix match. (The callback route's own allowlist check, above, is a separate mechanism from this gate — the gate governs *navigating to* `/admin`, the callback check governs whether a session should exist at all.)

**`middleware.ts`'s matcher excludes `/api` entirely** (`matcher: ["/((?!_next|api|.*\\..*).*)"]`). An admin-facing API route (e.g. `/api/admin/...`) would **not** be covered by the middleware gate and needs its own explicit `requireAdmin()` call — matching the existing "belt-and-suspenders" pattern already used in `app/admin/(protected)/layout.tsx` and every Server Action in `app/archive/actions.ts` and every write function in `lib/archive/index.ts` (see above), none of which trust the gate alone.

### Structured data (JSON-LD) — every archive page and the product page now describe their subject, not just breadcrumbs

Every archive detail page emits **two** JSON-LD objects (`<JsonLd data={[subjectJsonLd, breadcrumbJsonLd]} />`, `lib/shopify/structured-data.ts` despite the `lib/shopify` location — this file is the single place all JSON-LD is built regardless of domain, archive included): a `BreadcrumbList` (unchanged, existed before this) plus a subject-specific type built from exactly the fields the admin editors capture, nothing invented:

- Artist → `Person` (`buildPersonJsonLd`): `name`, `description` (bio), `image`, `url`.
- Publication → `CreativeWorkSeries` (`buildCreativeWorkSeriesJsonLd`): `name`, `description`, `image`, `datePublished` (the `issue_date` column — free text like `"Nov 1942"` or `"Fall 42"`, not strict ISO 8601; schema.org's Date properties accept plain Text, so this is valid markup but won't be machine-parsed for date-sensitive rich-result features), `url`.
- Artwork → `CreativeWork` (`buildArtworkCreativeWorkJsonLd`): `name`, `description`, `image`, `url`, plus nested `creator` (`Person`, the artist) and `isPartOf` (`CreativeWorkSeries`, the publication, if any). Deliberately `CreativeWork`, not the more specific `VisualArtwork` — chosen so the artwork's own canonical page agrees with every *reference* to it.

**The product page also links back into the archive**, via `buildProductJsonLd`'s third parameter (`artworks: ArtworkDetail[]`, from the new reverse lookup `getArtworksForProductHandle(handle)` — the only place in `lib/archive/index.ts` that queries `artwork_products` by handle instead of by artwork id) — added as `isBasedOn` on the `Product` node (not schema.org's `character`, which was tried first and reconsidered: `character` frames the artwork as depicted content, `isBasedOn` more precisely says "this product's design is derived from this work," correct for a manufactured shirt/print). The `creator`/`isPartOf` nesting is shared between `buildArtworkCreativeWorkJsonLd` and `buildProductJsonLd`'s `isBasedOn` via one internal helper (`buildArtworkCreatorAndSeries`) — don't let these drift apart by editing one without the other.

**One deliberate inconsistency, not a bug: `isBasedOn` never includes `image`, but the artwork's own page's `CreativeWork` does.** On the *product* page, a second unrelated image URL nested inside `isBasedOn` risks confusing Google's Product image requirements for rich results (which expect the product photo, not source art). On the artwork's *own* canonical page there's no such conflict — it's the image. Don't "fix" this asymmetry into consistency; it's the correct call in both places for different reasons.

Every optional field (`description`, `image`, `datePublished`, `isPartOf`) is `undefined` when absent, not `null` or `""` — relies on `JSON.stringify` dropping `undefined` keys, matching this file's existing convention throughout.

## Analytics & server-side conversion tracking

This store sends conversion events to GA4, Meta, and Reddit from **both** the browser (client-side pixels/GTM) and the server (Shopify webhooks → each platform's Conversions API). The server-side path exists because ad blockers and iOS privacy features suppress client-side pixels, so purchase events are duplicated server-side — each platform's server call includes an event/transaction identifier derived from the Shopify order id so the platform can dedupe against any client-side pixel that also fired.

### Client-side (`lib/analytics/ecommerce.ts`)

Thin wrappers around `sendGTMEvent` (from `@next/third-parties/google`) that push standard GA4 ecommerce events into GTM's dataLayer: `trackViewItem`, `trackAddToCart`, `trackRemoveFromCart`, `trackSearch`, `trackBeginCheckout`. GTM is loaded in `app/layout.tsx` via `gtmScriptUrl="https://data.weirdstrange.com/gtm.js"` (container `GTM-N99WWR99`) instead of the default `googletagmanager.com` script.

`data.weirdstrange.com` is a **real server-side GTM (sGTM) deployment** — DNS resolves to `ghs.googlehosted.com` (App Engine), Google's standard managed sGTM hosting — not merely a first-party proxy for the loader script. This means a genuine second GTM container (a "server" container, separate from the "web" container that holds `GTM-N99WWR99`'s client-side tags) exists and can receive forwarded events server-to-server.

Loading the web container through an sGTM URL does *not* by itself make that container's tags execute server-side — each tag still independently chooses to run client-side (calling `fbq()` in the browser, same as loading `gtm.js` from Google directly) or to be forwarded through the server container as a true server-side send (a Meta CAPI server tag). That configuration lives entirely at tagmanager.google.com and has no representation in this codebase.

**Confirmed working (verified via Meta Events Manager production data, not just GTM config inspection):** `ViewContent` and `AddToCart` are dual-sent — a client-side Meta Pixel tag *and* a server-side Meta Conversions API tag (Stape's "Facebook Conversion API" template, in the server container) both fire for each real event, sharing the same `event_id` (see below), and Meta correctly dedupes them into one counted event. Confirmed by pulling Meta's raw event-source-breakdown export: every row since the server-side tags went live shows `browser_received_count` exactly equal to `server_received_count`, for both event types, with zero mismatches. This means these two events are now immune to ad blockers/ITP — the server leg doesn't depend on the client leg surviving.

`Purchase` is the only event with a *confirmed* browser-independent path via a different mechanism — it goes through `lib/analytics/order-webhook.ts`'s direct server-to-server Conversions API calls (not GTM at all), triggered by Shopify's order webhook rather than any browser event. It is **not deduped** against any client-side Pixel `Purchase` fire — there is no order-confirmation page in this Next.js app (checkout happens entirely on Shopify's hosted checkout domain), no `fbq()` call anywhere in this repo, and no client-side `purchase` dataLayer event, so `order-webhook.ts`'s `event_id: String(order.id)` is unpaired today; it's defensive, not functioning dedup. Extending the `ViewContent`/`AddToCart` dual-send pattern to `Purchase` would require a client-side Pixel fire on Shopify's own checkout/order-status page — Shopify-side config, outside this repo, not attempted yet.

`pushEcommerceEvent()` generates a fresh `crypto.randomUUID()` per call and includes it as `event_id` on every dataLayer push (`view_item`, `add_to_cart`, `remove_from_cart`, `begin_checkout` — anything routed through this helper; `trackSearch` bypasses it and has no `event_id`). This is what the client Meta Pixel tags' Event ID field and the server Meta CAPI tags' automapped `event_id` both read, confirmed live for `view_item`/`add_to_cart` as above. `remove_from_cart`/`begin_checkout` have the `event_id` plumbing in code but their GTM tags haven't been checked/confirmed the same way — don't assume they're deduped without checking Events Manager the same way.

**Do not reuse `pushEcommerceEvent`'s `event_id` as a persistent visitor/session identifier.** It's intentionally single-use and disposable — generated fresh per call, meant only to pair one client-side fire with one server-side forward of the *same* event. A persistent anonymous-visitor ID is a different concept with a different lifecycle (established once, kept stable across a session); this codebase already has several purpose-specific versions of that (GA4's client_id via `_ga`, `_fbp`/`_fbc`, `_rdt_uuid`, Shopify's `cartId` cookie) — don't invent a new unified one without a specific reason, and never conflate it with the per-event dedup ID.

Don't add new client-side tracking calls without checking whether the corresponding server-side webhook event already covers it (avoid inventing more parallel event types than GA4/Meta/Reddit have documented equivalents for).

**GTM's linked web+server Preview mode does not auto-connect for this project — this is a known, reproduced dead end, not something to re-debug.** Normally, opening Preview on the web container (`GTM-N99WWR99`) is supposed to auto-detect the paired server container and attach an `X-Gtm-Server-Preview` header to outgoing requests so the server container's own Preview panel shows matching events live. For this project, that auto-linking never happens — confirmed via clean-restart retest (closing both Preview sessions, reopening server-first per Google's documented order, same-browser/same-Google-account session) and ruling out every checkable cause in this repo (`middleware.ts` doesn't touch `data.weirdstrange.com`, DNS/routing is correct, the Google Tag's `server_container_url` config is correct). The server container's own "Send requests manually" dialog (visible from its Preview screen) confirms the header-based mechanism itself works — a manual `curl` with that header populates the server Preview panel immediately — so this is specifically an auto-linking failure between the two containers, not a broken server container.

**Practical implication:** you cannot watch client and server tag firing live side-by-side while browsing normally. To inspect what actually reaches the server container for a specific request, either (a) run the exact `curl` command from the server container's "Send requests manually" dialog (a synthetic request, not real browsing — token must be freshly copied each Preview session, it's not stable), or (b) trust Meta Events Manager's own production data instead (Diagnostics → export the event-source-breakdown CSV, compare `browser_received_count` vs `server_received_count` per time bucket — equal counts on every row is definitive proof of correct dual-send and dedup, and doesn't depend on GTM Preview working at all). Do not spend time trying to fix the auto-link — already attempted a Chrome DevTools "Override headers" approach (fails, that UI can only edit headers already present on a request, not add new ones) and a `window.fetch` override via console (unreliable, since GA4/GTM's collect requests may go out via `sendBeacon`/`XHR` rather than `fetch`). A Service Worker could technically intercept and header-inject on all outgoing requests, but that's a large-blast-radius change (affects every request site-wide) for what's purely a debugging convenience — not worth it given Events Manager already gives ground-truth verification.

### The fbp/fbc/click-id cart-attribute bridge

**Problem this solves:** the server-side webhook handlers (`lib/analytics/order-webhook.ts`) fire from Shopify calling Vercel directly, long after checkout — there's no browser context, so they can't read first-party ad-click cookies (`_fbp`/`_fbc` for Meta, `_rdt_uuid`/`_rdt_cid` for Reddit, GA4's client_id from `_ga`) the way a client-side pixel could. Without those, server-side Purchase events only match on hashed email/phone, which scores much lower Event Match Quality on every platform.

**Mechanism:** Shopify Cart attributes are the only thing that survives from "browser has cookies" (checkout time) to "webhook fires with the completed order" (order-created time), because Shopify copies cart attributes onto the resulting Order as `note_attributes`.

- `lib/analytics/cookies.ts` — `getCookie(name)`, a minimal `document.cookie` reader. Don't grow this into a general cookie library; it's intentionally scoped to reading a few specific ad-platform cookie names.
- `components/cart/modal.tsx`'s `CheckoutButton` — right before redirecting to `cart.checkoutUrl`, reads `_fbp`, `_fbc`, `_rdt_uuid`, `_rdt_cid`, and derives a GA4 `client_id` from the `_ga` cookie (format `GA1.1.<id1>.<id2>` → GA4 wants just `<id1>.<id2>`, hence the `.split(".").slice(-2).join(".")`). Writes whichever are present as cart attributes via `updateCartAttributesAction` (`components/cart/actions.ts`, a Server Action wrapping `lib/shopify/index.ts`'s `updateCartAttributes`), racing against a timeout so a slow write never blocks the redirect to checkout.
- `lib/analytics/order-webhook.ts` — reads `order.note_attributes`, matches by name (`_fbp`, `_fbc`, `_rdt_uuid`, `_rdt_cid`, `_ga_client_id`), and feeds them into each platform's CAPI payload as **unhashed** fields (`fbp`/`fbc` for Meta, `uuid`/`click_id` for Reddit, `client_id` for GA4) — these are cookie/click identifiers, not PII, so unlike email/phone they are not hashed before sending.

**Known caveat, accepted as a tradeoff:** Shopify cart/note attributes don't always reliably survive onto the order (reported inconsistently by Shopify's own dev community). If an order's `note_attributes` is missing an expected key, that's this known limitation, not a bug — the code already falls back gracefully (e.g. GA4's `sendGA4Purchase` falls back to a synthetic `${order.id}.${order.id}` client_id when `_ga_client_id` is absent).

### "Do Not Sell or Share" opt-out (CCPA/CPRA)

Scoped deliberately to US-only requirements — an opt-out model (CCPA/CPRA: share by default, let users turn it off), not GDPR's opt-in model (consent required before any sharing). There is no cookie banner blocking tracking on first visit; that's intentional, not a missing feature, per this scoping decision.

**Mechanism:** a `privacy_opt_out` cookie (1-year max-age, set client-side) gates both the client-side and server-side tracking paths.

- `lib/analytics/cookies.ts` — `setDoNotSellOptOut(optedOut)` writes/clears the cookie; `hasDoNotSellOptOut()` reads it.
- `app/privacy-choices/page.tsx` + `components/privacy/do-not-sell-toggle.tsx` — the opt-out UI. `DoNotSellToggle` is a Client Component that reads the cookie in a `useEffect` (not during render) and renders `null` until mounted, to avoid an SSR/hydration mismatch — `document.cookie` doesn't exist on the server, so the server-rendered and first-client-render markup must match (both "nothing yet"). There's no site-wide banner or footer-embedded toggle component in this repo; the link to `/privacy-choices` lives entirely in Shopify's footer menu config (admin-editable there, not in code) — the page just has to exist and be reachable, not be persistently visible, which satisfies CCPA's "clear and conspicuous link" requirement without needing an intrusive banner.
- `lib/analytics/ecommerce.ts` — `pushEcommerceEvent()` (backing `trackViewItem`/`trackAddToCart`/`trackRemoveFromCart`/`trackBeginCheckout`) and `trackSearch()` both no-op immediately if `hasDoNotSellOptOut()` is true. This blocks the dataLayer push entirely, so neither the client Pixel tag nor the server-forwarded GTM tag fires — opting out doesn't just stop one leg of the dual-send, it stops the event from being generated at all.
- `components/cart/modal.tsx`'s `CheckoutButton` — when opted out, skips reading `_fbp`/`_fbc`/`_rdt_uuid`/`_rdt_cid`/`_ga` entirely (doesn't just withhold them — doesn't read them) and instead writes a single `_privacy_opt_out: "true"` cart attribute, which Shopify carries through to `order.note_attributes` the same way as the ad-click cookies (see bridge mechanism above).
- `lib/analytics/order-webhook.ts`'s `handleOrderCreated` — checks `order.note_attributes` for `_privacy_opt_out === "true"` and, if set, skips `sendGA4Purchase`/`sendMetaPurchase`/`sendRedditPurchase` entirely for that order.

**Deliberate scope boundary — this is a considered decision, not an inconsistency:** opting out gates only the three ad-platform sends (GA4/Meta/Reddit — third-party sharing, what CCPA/CPRA actually regulates). It does **not** gate `markAbandonedCheckoutCompleted` (`order-webhook.ts`) or the `checkouts/create` → abandoned-cart reminder email pipeline (`lib/analytics/checkout-webhook.ts`, deliberately left untouched by opt-out) — both are first-party order/marketing operations, not "sale or sharing" of data with a third party, so they're out of scope for this opt-out by design. Don't extend opt-out gating to those without re-confirming that's actually wanted; it was an explicit choice, not an oversight.

### Server-side webhooks (`lib/analytics/order-webhook.ts`, `app/api/webhooks/order-created/route.ts`)

Shopify's `orders/create` webhook → HMAC-verified (`isValidShopifyHmac`, using `SHOPIFY_WEBHOOK_SECRET`) → fans out via `Promise.allSettled` to `sendGA4Purchase`, `sendMetaPurchase`, `sendRedditPurchase`, and `markAbandonedCheckoutCompleted` (see below). Each platform function independently no-ops with a `console.error` if its env vars aren't configured, rather than throwing — so a misconfigured platform never blocks the others or fails the webhook response to Shopify.

Reddit-specific gotcha: the `_rdt_uuid` cookie value is `"<timestamp>.<uuid>"`; Reddit's CAPI only wants the UUID part, and it's validated against an RFC4122 regex before being sent (`isRfc4122Uuid`) — malformed/missing values are silently dropped rather than sent bad data.

`REDDIT_CAPI_TEST_ID` + a `test_id` field is only included when `VERCEL_ENV !== "production"`, so Preview/local webhook tests don't pollute real Reddit ad account data.

### Abandoned checkout recovery email

A second, related but independent pipeline — reminds customers by email if they enter an email at checkout and don't complete the purchase.

- `app/api/webhooks/checkout-created/route.ts` + `lib/analytics/checkout-webhook.ts` — Shopify's `checkouts/create` webhook (same HMAC pattern as order-created). **Important gotcha already hit once:** this payload has **no top-level `id` field** — Shopify identifies checkouts by `token` (a string), not a numeric id, unlike the Order resource. Also has no reliable top-level `total_price`; it's derived by summing `line_items[].line_price` when absent. Only upserts a row if `checkout.email` is present (no email = no way to send a reminder, skip entirely).
- Supabase table `abandoned_checkouts` (`id` is `text`, holding the checkout token) — see `supabase/migrations/2026081*_abandoned_checkouts*.sql`. RLS is enabled with **zero policies** — only the service-role key (`getSupabaseServerClient()`) can read/write it, since it holds customer emails and live checkout URLs. Never add an anon/authenticated policy to this table without a specific reason; nothing client-side should ever query it directly.
- `lib/analytics/order-webhook.ts`'s `markAbandonedCheckoutCompleted` — cross-references real orders against pending abandoned-checkout rows by matching `order.checkout_token` (not `checkout_id` — same token-vs-id distinction as above) and sets `order_id` on the matching row, so the reminder cron skips anyone who already completed checkout.
- `app/api/cron/abandoned-checkout-reminder/route.ts` — queries rows with `created_at` in a 45–75 minute-old window (a window, not just "> 1 hour", so a periodic poll doesn't double-send or miss the boundary), `reminder_sent_at IS NULL`, `order_id IS NULL`. Auth is a `Bearer ${CRON_SECRET}` header check — this must match **exactly** between Vercel's `CRON_SECRET` env var and whatever's calling it (see below).
- `lib/email/resend.ts` + `lib/email/abandoned-checkout.ts` — Resend client + HTML email (cart contents, CTA linking to `abandoned_checkout_url`), includes `List-Unsubscribe`/`List-Unsubscribe-Post` headers for CAN-SPAM compliance since this is a marketing-adjacent (not purely transactional) email.

**Why the cron lives in `cron-worker/`, not Vercel Cron:** Vercel's Hobby plan only allows once-daily cron schedules — a `*/15 * * * *` schedule in `vercel.json` causes every deploy to fail outright with a hard error, not a warning. `cron-worker/` is a **separate, standalone Cloudflare Worker** (its own `package.json`, `wrangler.jsonc`, deployed independently via `wrangler deploy`, not part of the Next.js build) whose only job is to `fetch()` the Vercel cron route every 15 minutes with the bearer secret. It is deliberately excluded from the root `tsconfig.json` (`exclude: ["cron-worker"]`) because it has its own Cloudflare Workers types (`ScheduledEvent`, `ExecutionContext` via `@cloudflare/workers-types`) that don't exist in the Next.js app's type environment — pulling it into the main typecheck breaks the build.

**Two independent secret stores that must match:** `CRON_SECRET` is set both in Vercel (env var, read by the Next.js route) and on the Cloudflare Worker (`wrangler secret put CRON_SECRET`). These are two separate systems with no automatic sync — if one is rotated without the other, the cron route silently 401s forever with no visible error except in Vercel's function logs. If the abandoned-checkout emails mysteriously stop sending, check this first via `wrangler secret list` (confirms it's *set*, not what it *is*) and comparing against Vercel's value (`vercel env pull` to a scratch file, never print the value in chat/logs).

## Deploying

`git push` to `main` triggers Vercel auto-deploy — but this has silently failed before (see cron-schedule failure above) with no obvious signal beyond the Vercel dashboard/CLI showing the last successful build is stuck on an old commit. When in doubt whether a deploy actually shipped, don't trust "I pushed" — verify with `npx vercel inspect <deployment-url> --logs | grep "Cloning github"` to confirm which commit actually built, or curl a known route and check for an unexpected 404 (route doesn't exist in the live build) vs the expected 401/200.

The `cron-worker/` Cloudflare Worker deploys independently via `cd cron-worker && npx wrangler deploy` — it is **not** triggered by pushes to `main` and has no CI wired up. A code change to `cron-worker/src/index.ts` sitting in git does nothing live until `wrangler deploy` is run manually.

## Layout structure — `Footer` lives in the root layout, not per-page

`<Footer />` is rendered exactly once, in `app/layout.tsx`, as a sibling of `<main>` — not inside it, and not imported individually by any page or nested layout. This matters because `<main>` carries `max-w-[1280px]` (`app/layout.tsx`): anything rendered inside `<main>` inherits that width cap, so a footer nested inside it cannot have full-viewport-width borders no matter what classes are applied within `footer.tsx` itself. If a footer styling change ever looks like it's being clipped or constrained, check `app/layout.tsx`'s `<main>` wrapper before assuming the bug is in `components/layout/footer.tsx`.

Don't re-add a per-page `import Footer from "components/layout/footer"` — every page used to do this (a leftover from before the App Router root-layout pattern was fully leaned on here), which also meant any page that forgot the import silently shipped without a footer (this happened to `/account` and `/privacy-choices`). Rendering it once in the root layout makes that class of bug structurally impossible instead of relying on every new page remembering to add it.
